# data/ ディレクトリ

## feedback.csv ★最重要

**TikTok動画を出すたびに1行足してください。**

現在このプロジェクトに一番足りていないのが、このデータです。
「どの通知が動画になり、その動画が何回再生されたか」の記録が無いと、
検知の精度が上がったかどうかを判定する手段がありません。
閾値をどれだけ調整しても「良くなったか分からない」ままになります。

| 列 | 意味 |
|---|---|
| `notified_at` | 通知が来た日時 (例: 2026-08-24 15:30) |
| `post_url` | 元になったX投稿のURL |
| `buzz_score` | 通知に表示されていたスコア |
| `genre` | 通知に表示されていたジャンル |
| `made_video` | 動画にしたか (`yes` / `no`) |
| `minutes_after` | X投稿から何分後に動画を出せたか |
| `views` | TikTokの再生数(投稿から24時間後の値がおすすめ) |
| `likes` | TikTokのいいね数 |
| `followers_gained` | その動画から増えたフォロワー数 |
| `note` | 自由記述(動画にしなかった理由など) |

**`made_video=no` の行も必ず残してください。**
「通知は来たが使えなかった」という記録が、
そもそも通知すべきでなかったパターンを見つける材料になります。

月に一度、このファイルをGrokに読ませてください
(→ `docs/grok_prompts.md` の **プロンプト⑤**)。

編集はGitHub上で直接できます。ファイルを開いて鉛筆アイコンをタップするだけです。

## log/YYYY-MM-DD.jsonl

実行のたびに、スコア上位10件と実際に通知した投稿が自動で追記されます。
**通知した/しなかったの両方が入っている**のがポイントで、

- 通知したのに伸びなかった → 閾値が低すぎる
- 通知しなかったが実は伸びた → 閾値が高すぎる

を後から検証できます。3日分たまったらGrokに分析させてください
(→ `docs/grok_prompts.md` の **プロンプト④**)。

こちらは自動生成なので、手で編集する必要はありません。

## monitor.db (Gitには入りません)

伸び率の計算に使う観測履歴のSQLiteデータベースです。
GitHub Actionsのキャッシュ経由で実行間で引き継がれます。
24時間より古い記録は自動で削除されます。

キャッシュが消えると伸び率は一時的に「推定値」に戻りますが、
数回の実行で自動的に復旧するので、特に対応は不要です。
