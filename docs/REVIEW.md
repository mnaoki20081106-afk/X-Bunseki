# プロジェクト診断レポート (2026-08-23)

実行履歴49回分(2026-08-21 08:55 〜 08-23 12:59、status.jsonのコミット履歴)と
全ソースコードを読んだ上での診断です。

---

## 0. 結論を先に

**「思ったような結果が出ない」原因は、閾値の高さではなく設計の構造です。**
主因を1つ挙げるなら、**このシステムは伸び率を一度も計算していませんでした。**

プロジェクトの目的は「統計と伸び率の計算で早期発見すること」ですが、
実際のコードは伸び率(＝時間あたりの増加量)ではなく
**「投稿からの平均速度」**しか計算していませんでした。
その差を測るには同じ投稿を複数回観測して差分を取る必要がありますが、
データベースには**通知した投稿しか保存されていなかった**ため、
差分を計算する材料がそもそも存在しませんでした。

## 2. 見つかった問題と、それぞれの対応

### 問題1 ★最重要 : 伸び率を計算していなかった

`detector.py` の速度計算はこうなっていました。

```python
def _velocity(count, hours):
    return count / max(hours, 0.25)   # いいね総数 ÷ 投稿からの経過時間
```

これは「投稿してから今までの平均」であって、伸び率ではありません。
**投稿直後に跳ねて既に完全に失速した投稿でも、この値は高いまま**です。
早期発見どころか、終わったバズを掴んでしまいます。

さらに `db.upsert_post()` は通知直前にしか呼ばれておらず、
**判定に落ちた投稿は毎回そのまま捨てられていました。**
次の実行では同じ投稿をゼロから収集し直すので、
「前回から何件増えたか」は原理的に計算できませんでした。

**対応**
- `observations` テーブルを追加し、**収集した全投稿**を毎回記録するようにした
- `growth.py` を新設し、前回観測との差分から
  `いいね/分` と `加速度(今の区間速度 ÷ 前の区間速度)` を実測するようにした
- 加速度が1.0未満＝失速中の投稿は、数字が大きくてもスコアが下がる

### 問題2 : 入口が `min_faves:500` だった(早期発見が原理的に不可能)

検索クエリは1本だけでした。

```
lang:ja min_faves:500 min_replies:20 -filter:retweets
```

**すでに500いいね付いた投稿しか入口を通れない**設計です。
「バズる前に見つける」を掲げながら、入口が遅行指標になっていました。

**対応**
- `keywords.txt` を `(地震 OR 台風 OR 速報 OR ...)` というOR句に変換し、
  **Xのサーバー側でジャンルを絞らせる**方式に変更(`keyword_filter.query_groups()`)
- ジャンルが絞れているぶん `min_faves` を **500 → 50** まで下げられる
- 結果、「まだ小さいが伸びている投稿」が入口を通れるようになった

### 問題3 : AND条件の掛け算で、確率的にほぼ絶対に通らなかった

v3.4の判定はこうでした。

```
持続バズ = いいね速度 AND インプレッション20万 AND 返信率4.5% AND (BM20 or 引用10)
瞬間バズ = いいね1800 AND RT150 AND 返信70
```

各条件の通過率が仮に3割だとすると、4条件ANDでは 0.3⁴ = **0.8%**。
条件を1つ足すたびに通過率が指数的に落ちます。
コメントに残っている調整の履歴(v3 → v3.1 → v3.2 → v3.3 → v3.4)は、
**AND構造そのものが原因なのに、個々の閾値を上下させ続けていた**記録です。
これはどれだけ繰り返しても収束しません。

**対応**
- **加重スコア1本(0〜100点) + 閾値1つ**に置き換えた
- 調整すべきツマミが12個 → **1個(`NOTIFY_SCORE`)** になり、感度を連続的に動かせる
- 配点: 伸び率40 / 加速度15 / 議論量15 / 保存率10 / 拡散率10 / 関連度10

### 問題4 : ブックマーク数のパースが壊れていた

`_fetch_detail_stats()` は「"Views"以降に出てくる**4番目の数字**」を
ブックマーク数として読んでいました。位置頼みのパースです。
実際に記録されていたデータを見ると壊れているのが分かります。

| 投稿 | いいね | 記録されたブックマーク |
|---|---|---|
| @Ex_Albio | 8,208 | **8,800** |
| @VanilLa_sub | 7,279 | **7,700** |
| @mikochisub | 5,048 | **5,000** |

**ブックマークがいいねを超える**のは現実にはまず起きません。
UI要素が1つ増減しただけで全く別の値が入り込んでいました。
しかもこの値は「激アツ判定」と「持続バズ判定」の両方に使われていたので、
判定を直接歪めていました。

**対応**
- 位置ではなく**ラベルで**取る方式に変更
  (アクションバーの `aria-label` から「◯件のブックマーク」を正規表現で抽出)
- `sanitize_counts()` を追加し、`ブックマーク > いいね` のような
  ありえない値は0に落とす(誤った巨大な値より、欠損の方が害が小さい)
- ついでに、これまで詳細ページを1件ずつ開いていた処理の大半が不要になった

### 問題5 : 同じ出来事で何度も通知していた

8/22 17:36 に8件、18:49 に5件。中身は全て同じ地震でした。
受け取る側からすると1つの出来事なのに13回鳴ります。

**対応**
- `clustering.py` を新設。本文の文字bigramのOverlap係数で同一話題をまとめ、
  **1話題1通知**にした
- 直近8時間に通知した話題と似ている投稿も除外する
- 1回の実行あたり最大2件、24時間で最大12件の上限も追加

これにより「感度を上げても通知が溢れない」状態になったので、
閾値を下げる余裕が生まれました。

### 問題6 : 通知に「何が起きたか」が書かれていなかった

届いていた通知はこれだけです。

```
🔥 急上昇検知 [持続/その他]
someone の投稿が0.5時間でいいね1,234・引用0・ブックマーク0
https://x.com/...
```

**投稿の本文が一切入っていません。** 何の話題なのか分からないので、
必ずXを開いて確認する手間が発生します。
スクープ動画は気づいてから最初の数分が勝負なので、これは致命的なロスです。

**対応** — 通知を見た瞬間に撮り始められる情報を全部入れた。

```
🔥🔥🔥 激アツ [事件・事故] 78点
⏱ 投稿から34分 / いいね3,200 +94/分 加速1.6x
💬310 🔁640 🔖420 👁180,000

📰 (LLMによる50字要約)
「投稿本文の冒頭120字...」
@handle

🎬 タイトル案: 【速報】...
🎤 掴み: これ、まだニュースになってません
📊 スクープ度8/10 解説需要7/10 動画適性9/10 🟡リスク中
🧮 議論量15 / 伸び率31 / 加速度12
🗂 同じ話題の投稿が他に3件伸びています
```

### 問題7 : LLMの使い道がゴールとずれていた

`genre_classifier.py` は通知確定後に「スポーツ/芸能/政治…」を分類していました。
しかし**ジャンル名は動画を作る判断材料になりません。**

このプロジェクトのゴールは「バズ投稿の検知」ではなく
「需要のあるTikTok動画を作ってフォロワーを獲得すること」です。
LLMに聞くべきなのは、動画のネタとして成立するか・どう撮るか、です。

**対応**
- `content_scorer.py` に置き換え。スクープ度・解説需要・動画適性・
  リスク・掴み・タイトル案を返させる
- クラスタリング後の上位3件だけに呼ぶので、Groq無料枠で十分足りる

### 問題8 : 実行頻度が伸び率の計算に足りていなかった

毎時実行では、同じ投稿を2回観測するまで最短1時間かかります。
その頃にはバズは終わっています。

さらに、このリポジトリは **Public** なので
GitHub Actionsの実行時間は**無制限で無料**でした。
毎時に抑える理由(Privateの2,000分/月制約)はそもそも存在しませんでした。

**対応** — 15分間隔(`7,22,37,52 * * * *`)に変更。
投稿から30分の時点で既に2〜3回観測でき、加速中かどうか判断できます。
併せて `concurrency` と push のリトライを追加(実行が重なる可能性が出たため)。

### 問題9 : テストが1つも無かった

「通知が来ない」原因が収集の失敗なのか判定ロジックなのか、
切り分ける手段がありませんでした。

**対応** — `tests/test_pipeline.py` を追加(24件)。
Xにアクセスせず数秒で終わります。ここが通っていれば
「原因は収集側」と即断できます。push毎にCIで自動実行します。

## 4. 運用の手順(ここからが本番)

コードの改善だけでは足りません。**閾値は実データでしか決まりません。**

### 最初の2〜3日: 観察に徹する

`NOTIFY_SCORE` の初期値55点は根拠のある推定値ですが、あくまで推定です。
まずは通知の量を見てください。

- **多すぎる** → `NOTIFY_SCORE` を60〜65に上げる
- **少なすぎる** → 50に下げる
- **変更方法**: Settings → Secrets and variables → Actions → **Variables** タブ →
  `NOTIFY_SCORE` を追加。**コードを触る必要はありません。**

### そのあと: `data/log/` を使って検証する

毎回、スコア上位10件が `data/log/YYYY-MM-DD.jsonl` に記録されます。
通知したもの・しなかったものが両方入っているので、

- 通知したのに伸びなかった → 閾値が低すぎる
- 通知しなかったが実は伸びた → 閾値が高すぎる

が後から検証できます。

生ログは1日約1,000行になるのでそのままでは貼れません。
**Actions タブ →「Grok用レポート作成」→ Run workflow** を実行すると、
`data/grok_report.md` にGrokへ貼れるサイズの要約が生成されます。
各投稿の「15分おきの軌跡」と「スコア」「最終的にどれだけ伸びたか」が
対応付いているので、**スコアが当たっていたかの答え合わせ**ができます。
これをGrokに分析させてください(→ `docs/grok_prompts.md` の プロンプト④)。

### 最も重要: 動画の結果を記録する

**これが今このプロジェクトに一番足りていないものです。**

現状、「どの通知が実際に動画になり、その動画が何回再生されたか」の
記録がどこにもありません。つまり
**検知の精度が上がったかどうかを判定する手段が無い**状態です。

`data/feedback.csv` に、動画を出すたび1行足してください。
月に一度これをGrokに読ませれば、
「どんな通知が当たりで、どんな通知が外れか」が数字で分かります。
そこまで来て初めて、閾値ではなく**キーワードとジャンル選定**を
根拠を持って直せるようになります。

## 5. 正直に言っておくべきこと

### 5-1. 地震・災害ネタに寄りすぎている

現在の `keywords.txt` は、実測でほぼ「地震」「速報」しか当たっていません。
しかし災害ニュースは、

- 全メディアが数分で報じるのでスクープになりにくい
- TikTokの収益化・コミュニティガイドライン上、扱いが難しい
- 視聴者が「解説」を求めるタイプの話題ではない

という、**TikTokのスクープ・解説動画には最も向かないジャンル**です。

一方で `熱愛` `不倫` `炎上` `暴露` `疑惑` といった、本来ど真ん中のワードは
`min_faves:500` に阻まれてほぼ入口を通れていませんでした。
v4で `min_faves:50` にしたので通るようになるはずですが、
**どのジャンルを狙うかは、あなたが決める必要があります。**
これはGrokに相談するのに最適なテーマです(→ プロンプト②)。

### 5-2. Xのアカウント凍結リスクは上がっています

15分間隔にしたことで、Xへのアクセスは毎時4倍になりました。
ダミーアカウント運用は今まで以上に必須です。
凍結が心配なら `*/20` や `*/30` に下げてください
(伸び率の精度は落ちますが、毎時よりはずっと良いです)。

### 5-3. LINEの無料枠に注意

LINE Messaging APIの無料プランは**月200通**です。
1日12通の上限でも月360通で超過します。
**メインの通知はPushoverにして、LINEは「動作確認」用に留める**のが安全です。
気になるなら `NOTIFY_MAX_PER_DAY` を6に下げてください。

### 5-4. Xの画面構造への依存は残ったままです

ラベルベースのパースにしたことで壊れにくくはなりましたが、
Xが仕様変更すれば止まります。
「3回連続で0件」のアラートは維持してあるので、届いたら教えてください。

### 5-5. v4の閾値もまだ「推定値」です

今回の変更で構造の問題は直りましたが、
**具体的な数値(55点、150いいね、120いいね/分)は実データで検証していません。**
これらは `data/log/` が数日分たまってから調整するものです。
最初の数日で通知量が極端になっても、それは想定内です。
