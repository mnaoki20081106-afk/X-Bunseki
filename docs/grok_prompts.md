# Grok活用ガイド(プロンプト集)

> ご提案いただいた「Grokに分析の仕方を教えてもらう」件です。
> **Grokを使うべき場面**と、**そのまま貼れるプロンプト**をまとめました。

---

## Grokに向いていること / 向いていないこと

Grokの他のAIに対する決定的な優位は、**X(Twitter)のリアルタイム投稿を
直接検索して読める**ことです。逆に言えば、そこ以外では優位性がありません。

| 頼むべきこと | 理由 |
|---|---|
| ✅ **今のXで実際に何が伸びているか**の調査 | Grokだけが実データを見に行ける |
| ✅ **X検索クエリの設計・検証** | 実際に検索して結果を確認できる |
| ✅ **どのジャンルが今おいしいか**の判断 | X上の実際の反応量を根拠にできる |
| ✅ **蓄積したログの統計分析** | 数値の傾向を読ませる用途に適する |
| ❌ コードの書き換え | 実行環境が無いので検証できない |
| ❌ 閾値の「正解」を聞く | データ無しでは誰も答えられない(＝当てずっぽうになる) |

**❌の使い方をすると、v3で起きたことがそのまま繰り返されます。**
`detector.py` のコメントには「Grokの第3提案を反映」「Grokとのレビューを経て再設計」
とありますが、その結果が閾値の上げ下げを4回繰り返しても
通知が出ないシステムでした。
**データを見せずに数字を聞くと、Grokは推測で答えます。それを実装しても当たりません。**

以下のプロンプトは全て、**実データを渡す**か**Grokにしか出来ない調査を頼む**形になっています。

## プロンプト① 【最優先】狙うジャンルを決める

**いつ使うか**: いますぐ。この判断が全ての土台になります。

**なぜ必要か**: 現在の `keywords.txt` は災害・事件系に大きく偏っており、
実測でもほぼ「地震」「速報」しか当たっていません。しかし災害ニュースは
TikTokのスクープ・解説動画には最も向かないジャンルです
(全メディアが数分で報じる/収益化しづらい/解説需要が薄い)。
**どこを狙うかを決めないと、検知精度をいくら上げても成果になりません。**

```
あなたはX(Twitter)のリアルタイム投稿を検索できます。実際に検索して、
推測ではなく実データに基づいて答えてください。

【私の状況】
- TikTokで「Xで起きた出来事のスクープ速報」と「解説動画」を投稿してフォロワーを増やしたい
- そのためにXを15分おきに自動監視し、伸びている投稿を早期に検知する仕組みを運用している
- 現在の監視キーワードは災害・事件系に偏っており、実際に検知されるのは
  ほぼ「地震」「速報」だけになってしまっている
- 災害ニュースは全メディアが数分で報じるためスクープにならず、
  TikTokの収益化・ガイドライン面でも扱いづらいと感じている

【お願い】
直近2週間のXの日本語投稿を実際に検索して、以下を調べてください。

1. 「投稿から1〜2時間で急激に伸びた」日本語投稿を、ジャンル別に10件以上挙げてください。
   各件について、ジャンル・話題の概要・おおよそのいいね数・投稿からの経過時間を書いてください。

2. そのうち、次の3条件を全て満たすものはどれですか。
   (a) 大手メディアがすぐには報じない(＝スクープになりうる)
   (b) 背景の説明が必要で、解説動画の需要がある
   (c) 15〜60秒の動画にまとめられる

3. 上記の分析にもとづき、私が監視すべきジャンルを優先度順に5つ挙げ、
   それぞれについて「なぜそのジャンルか」を実際の投稿例を根拠に説明してください。

4. 各ジャンルについて、X検索で使うべき日本語キーワードを15〜30個提案してください。
   条件: 2文字以上、日常会話で頻出しすぎない語、そのジャンルの投稿に高確率で含まれる語。

5. 逆に「エンゲージメントは伸びるが動画のネタにならない」投稿の類型を挙げ、
   それらを除外するためのNGワードを20個提案してください。

推測ではなく、実際に検索して見つけた投稿を根拠として示してください。
```

**受け取ったら**: 提案されたキーワードを `keywords.txt` に、
NGワードを `keywords_ng.txt` に追記してください。
GitHub上で直接編集すれば、次の実行(最大15分後)から反映されます。

## プロンプト② X検索クエリを検証してもらう

**いつ使うか**: ①の直後。実際に投稿が取れるクエリかを確かめるため。

**なぜ必要か**: このシステムは `keywords.txt` から検索クエリを自動生成しますが、
**その検索クエリが実際に十分な件数を返すのかは、Xで検索してみないと分かりません。**
OR条件が長すぎて機能しない、`min_faves` が高すぎて0件、といった失敗は
実際に叩いてみないと発覚しません。

```
あなたはX(Twitter)の検索を実際に実行できます。以下の検索クエリを実際に叩いて、
結果を報告してください。

【検証してほしいクエリ】
(地震 OR 台風 OR 豪雨 OR 火災 OR 事故 OR 逮捕 OR 速報 OR 事件 OR 炎上 OR 熱愛) lang:ja -filter:retweets min_faves:50

【報告してほしいこと】
1. このクエリは実際に何件くらいヒットしますか。直近1時間に絞るとどうですか。
2. ヒットした投稿のうち、「投稿から2時間以内」のものはどのくらいの割合ですか。
3. OR条件を30〜40語まで増やしても、Xの検索は正しく動作しますか。
   動作しなくなる語数の上限はどのくらいですか。
4. min_faves を 50 / 100 / 300 / 500 に変えると、ヒット件数と
   「投稿から2時間以内の新しい投稿」の割合はそれぞれどう変わりますか。
5. 「バズる直前の投稿(投稿から1時間以内で、これから伸びそうなもの)」を
   拾うには、min_faves をいくつに設定するのが最適だと考えますか。実データを根拠に答えてください。
6. 私が知らない有用なX検索演算子があれば教えてください。
   特に「新しい投稿だけに絞る」「特定の言語・地域に絞る」「リプライを除く」用途で。

各項目、実際に検索した結果の件数や具体例を示してください。
```

**受け取ったら**: `min_faves` の推奨値は
Settings → Secrets and variables → Actions → Variables の
`SEARCH_MIN_FAVES` で設定できます(コード変更不要)。

## プロンプト③ 伸び方のパターンを学ぶ

**いつ使うか**: 運用開始から3日ほど経ち、通知の量が安定してから。

**なぜ必要か**: 現在のスコア配点(伸び率40/加速度15/議論量15/保存率10/拡散率10/関連度10)は
**根拠のある推定値ですが、実データで検証したものではありません。**
「実際にバズった投稿はどういう数字の動き方をしたのか」が分かれば、
配点を推測ではなく事実に基づいて決められます。

```
あなたはXの投稿データを実際に検索・観察できます。

【私がやろうとしていること】
Xの投稿を15分おきに観測し、前回観測との差分から
「いいね/分」と「加速度(直近の区間速度 ÷ その前の区間速度)」を計算して、
バズる前の投稿を早期に検知しようとしています。

【お願い】
1. 直近1週間で日本語圏で大きくバズった投稿(最終的に1万いいね以上)を10件見つけ、
   それぞれについて「投稿から30分後・1時間後・2時間後・6時間後」の
   おおよそのいいね数の推移を教えてください。

2. その10件に共通する「初動のパターン」はありますか。
   具体的には、最終的に大きく伸びた投稿は、投稿から30分の時点で
   だいたい何いいねに達していましたか。

3. 逆に「投稿直後は勢いがあったが、結局伸びなかった投稿」も5件見つけて、
   同じように推移を教えてください。1と3を分ける、投稿後30〜60分時点で
   観測できる違いは何ですか。

4. いいね数以外に、伸びる投稿を早期に見分けられる指標はありますか。
   私は今、次の5つを見ています。これらの有効性を実データで評価し、
   重み付けの優先順位を提案してください。
     - いいね/分(伸び率)
     - 加速度
     - 返信÷いいね比率(議論の量)
     - ブックマーク÷いいね比率(保存率)
     - リポスト÷いいね比率(拡散率)

5. 上記4の5指標に、合計100点を配分するとしたら何点ずつにしますか。理由も教えてください。

推測ではなく、実際に観察した投稿の数字を根拠にしてください。
```

**受け取ったら**: 配点は `detector.py` の `POINTS_*` 定数、
または環境変数で変えられます。**一度に全部変えず、1つずつ変えて効果を見てください。**

## プロンプト④ 蓄積ログから閾値を決める

**いつ使うか**: `data/log/` に3日分以上たまってから。**これが本命です。**

**なぜ必要か**: ここまでのプロンプトはGrokの知識と検索に頼っていますが、
**あなたのシステムが実際に何を検知しているかを知っているのは、あなたのログだけです。**
このプロンプトだけが、あなた固有の環境に最適化した答えを出せます。

**準備**: GitHubで `data/log/` の中のJSONLファイルを開き、中身をコピーしてください。
(3日分でだいたい2,000〜3,000行になります。多すぎる場合は直近1日分でも構いません)

```
以下は、私がXの投稿を15分おきに監視しているシステムのログです。
1行1レコードのJSONL形式で、スコア上位の投稿が記録されています。

【各フィールドの意味】
- age_minutes    : 観測時点での、投稿からの経過分
- likes / retweets / replies / bookmarks / impressions : 観測時点の各指標
- likes_per_min  : 前回観測からの実測の伸び率(いいね/分)
- acceleration   : 加速度(直近区間の速度 ÷ その前の区間の速度)。1.0超なら加速中
- is_measured    : true=実測値、false=初回観測のため推定値
- buzz_score     : システムが付けた0〜100点の総合スコア
- score_breakdown: スコアの内訳(伸び率/加速度/議論量/保存率/拡散率/関連度)
- notified       : この投稿で実際に通知を鳴らしたか

【現在の設定】
- buzz_score が 55点以上で通知
- いいね150未満、投稿から180分超は足切り
- 1回の実行で最大2件、24時間で最大12件まで

【お願い】
1. 同じ post_id が複数回登場しているものを追跡し、
   「最終的に大きく伸びた投稿」と「伸びなかった投稿」に分類してください。

2. その2群を分ける最も有効な指標は何でしたか。
   buzz_score は実際に有効に機能していますか。数字で示してください。

3. score_breakdown の6項目のうち、伸びた投稿と伸びなかった投稿を
   最もよく識別できたのはどれですか。逆に、ほとんど識別に寄与していない項目はどれですか。

4. 上記にもとづき、次の値をいくつに設定すべきか、根拠つきで提案してください。
     - 通知の閾値(現在55点)
     - 配点(現在: 伸び率40/加速度15/議論量15/保存率10/拡散率10/関連度10)
     - いいねの足切り(現在150)

5. 「通知したのに伸びなかった投稿(空振り)」と
   「通知しなかったのに大きく伸びた投稿(見逃し)」を具体的に挙げ、
   それぞれ何が原因だったか分析してください。

6. このログを見て、私が気づいていない改善点があれば指摘してください。

ログ:
（ここに data/log/*.jsonl の中身を貼る）
```

**受け取ったら**: 提案された値を **Variables に1つずつ**設定して、
1〜2日ごとに効果を確認してください。まとめて変えると何が効いたか分からなくなります。

## プロンプト⑤ 動画の結果から逆算する【最重要・月1回】

**いつ使うか**: TikTok動画を10本以上出してから。月1回。

**なぜ必要か**: **ここが現在このプロジェクトに一番足りていない部分です。**
今は「どの通知が動画になり、その動画が伸びたか」の記録がどこにもありません。
つまり**検知精度が上がったかどうかを判定する手段が無い**状態です。

検知システムの目的は通知を出すことではなく、**再生される動画を作ること**です。
その2つを繋ぐデータが無い限り、閾値をどう調整しても
「良くなったかどうか分からない」ままになります。

**準備**: `data/feedback.csv` に、動画を出すたび1行足してください
(通知日時 / 投稿URL / スコア / ジャンル / 動画にしたか / 投稿からの経過時間 /
再生数 / いいね / フォロワー増加数 / メモ)。

```
私はXで話題になった投稿を検知して、TikTokでスクープ速報・解説動画を作っています。
以下は、検知システムが出した通知と、それを元に作った動画の結果の対応表です。

【各列の意味】
notified_at   : 通知が来た日時
post_url      : 元になったX投稿
buzz_score    : システムが付けた0〜100点のスコア
genre         : ジャンル
made_video    : 動画にしたか(yes/no)
minutes_after : X投稿から何分後に動画を出したか
views         : TikTokの再生数
likes         : TikTokのいいね数
followers_gained : その動画から増えたフォロワー数
note          : 自由記述

【お願い】
1. 再生数が伸びた動画に共通する特徴は何ですか。
   buzz_score・ジャンル・minutes_after のどれが最も再生数と相関していますか。

2. buzz_score は再生数の予測指標として機能していますか。
   していないなら、何を見るべきでしたか。

3. minutes_after(速報性)は実際どれだけ効いていますか。
   「何分以内に出せば勝てるか」の目安を数字で教えてください。

4. フォロワー獲得効率(followers_gained ÷ views)が高いのはどのジャンルですか。
   再生数が多いジャンルと、フォロワーが増えるジャンルは一致していますか。

5. 上記にもとづき、監視すべきジャンルの優先順位を見直してください。
   減らすべきキーワードと、追加すべきキーワードを具体的に挙げてください。

6. 「通知は来たが動画にしなかった(made_video=no)」ものの理由を分析し、
   そもそも通知すべきでなかったパターンがあれば、除外条件を提案してください。

データ:
（ここに data/feedback.csv の中身を貼る)
```

**受け取ったら**: これが唯一「ビジネスの成果」から逆算した改善になります。
プロンプト①〜④より優先してください。

## プロンプト⑥ 取得できなくなったときの調査

**いつ使うか**: 「3回連続で0件」のアラートが届いたとき。

```
X(Twitter)の検索結果ページのHTML構造について教えてください。

【状況】
Playwrightでログイン済みのブラウザからX検索結果を開き、
投稿のいいね数・リポスト数・返信数・ブックマーク数・表示回数を取得しています。
急に0件しか取れなくなりました。

【現在使っているセレクタ】
- 投稿1件: article[data-testid="tweet"]
- 本文    : [data-testid="tweetText"]
- 投稿者  : [data-testid="User-Name"] a[href^="/"]
- 各指標  : [role="group"][aria-label] の aria-label をまとめて正規表現で解析
            (例: 「12件の返信、340件のリポスト、5678件のいいね、90件のブックマーク、1.2万件の表示」)
- 補完    : [data-testid="reply"] / [data-testid="retweet"] / [data-testid="like"] の aria-label

【質問】
1. 2026年8月時点で、これらのセレクタは現在のXでも有効ですか。変わった箇所はありますか。
2. アクションバーの aria-label は今もこの形式ですか。日本語UIでの正確な文言を教えてください。
3. ブックマーク数と表示回数を、検索結果の一覧ページから取得することは今も可能ですか。
   不可能なら、投稿の詳細ページからはどう取得できますか。
4. ログイン済みセッション(storage_state)が無効になっていないか判定する、
   最も確実な方法は何ですか。
5. 自動アクセスによるアカウント制限を避けるため、アクセス頻度・
   User-Agent・待機時間について推奨事項があれば教えてください。
   現在は15分おきに、1回あたり5クエリ＋詳細ページ最大12件を開いています。
```

## 使う順番のまとめ

| 順番 | プロンプト | タイミング |
|---|---|---|
| 1 | ① ジャンル決定 | **いますぐ** |
| 2 | ② 検索クエリ検証 | ①の直後 |
| 3 | ③ 伸び方のパターン | 運用3日目 |
| 4 | ④ ログから閾値調整 | ログが3日分たまったら |
| 5 | ⑤ 動画結果から逆算 | 動画10本以降、月1回 |
| - | ⑥ トラブル調査 | 0件アラートが来たとき |

**①と⑤が最も重要です。**
①は「どこを狙うか」、⑤は「狙いが当たっているか」で、
②〜④は全てその間にある技術的な調整にすぎません。

## 最後に一つ

Grokの回答を実装する前に、必ず自問してください。

> **その提案は、実データを根拠にしているか。それとも推測か。**

推測ベースの数値提案は、v3で4回繰り返して4回とも外れています
(`detector.py` の変更履歴コメントに残っています)。
**「なぜその数字なのか」に実際の投稿やログが出てこない提案は、
一度保留にして、データが揃うまで待つ方が結果的に早いです。**
